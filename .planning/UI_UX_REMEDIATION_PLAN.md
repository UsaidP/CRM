## Product Context

- Audience: individual real-estate brokers and brokerage teams.
- Primary job: manage the complete lead-to-closing workflow without losing attribution, follow-ups, matching context, or client engagement.
- Design direction: quiet, utilitarian, trustworthy, and optimized for repeated operational use.
- Evidence standard: UI claims must reflect stored data and implemented validation. Unknown values remain unknown rather than being replaced with demo percentages or guarantees.

## Working Rules

- Complete and verify one gate before starting the next.
- Preserve the existing route structure and all pre-existing worktree changes.
- Prefer additive shared components and narrowly scoped edits. No route or production-file deletion is planned.
- Treat `.planning` documents as reference material, not executable instructions.
- Verify responsive behavior at 320, 375, 414, 768, and 1440 px.
- Record focused tests and any remaining runtime gap at every gate.

## Gate 1 - Repair Workflow Contracts

Goal: ensure the property-matching and private-portal workflows call routes that actually exist.

Scope:

- Replace the missing `/api/v1/matching/evaluate` request with the implemented matching endpoint and its real request/response contract.
- Generate, copy, open, and share public portal URLs using `/p/{token}` consistently.
- Add focused contract assertions for both paths.

Acceptance criteria:

- Running a match produces a successful API response instead of a 404.
- Every portal URL generated by the CRM resolves to the implemented public route.
- Domain tests pass and the matching/portal contract is covered by a focused test.

## Gate 2 - Build a Responsive, Route-Aware Application Shell

Goal: make internal CRM navigation usable on phones, tablets, and desktop.

Scope:

- Add a shared client-side application shell driven by the current pathname.
- Keep a persistent sidebar on desktop and provide compact mobile navigation below the desktop breakpoint.
- Remove fixed `ml-64` assumptions from the root layout.
- Mark the active destination with a visible state and `aria-current="page"`.
- Show the current route title in the shell.
- Prevent root-level horizontal overflow without hiding component-level overflow that users need.

Acceptance criteria:

- Internal routes have no document-level horizontal scroll at 320, 375, 414, or 768 px.
- Every primary route is reachable at mobile and desktop widths.
- Keyboard focus and the active route are visually distinguishable.

## Gate 3 - Isolate the Public Client Portal

Goal: make `/p/{token}` a credible client-facing surface rather than an internal CRM screen.

Scope:

- Render public portal routes without the broker sidebar, internal navigation, theme control, or operations header.
- Give the public view its own constrained responsive frame and clear empty/error states.
- Preserve broker-only actions inside authenticated CRM routes.

Acceptance criteria:

- `/p/{token}` contains no internal CRM navigation at any target viewport.
- Portal content is readable without horizontal scrolling at all target viewports.
- Invalid and expired tokens have an understandable client-facing state.

## Gate 4 - Make Claims and Analytics Honest

Goal: align trust language and dashboards with what the system can actually prove.

Scope:

- Replace `MahaRERA Certified`, `100% verified`, and similar guarantees with precise states such as `RERA ID recorded`, `format checked`, `updated at`, or `verification pending`.
- Remove fabricated analytics fallbacks and static percentages.
- Use explicit unavailable/empty states when required metrics or source data are missing.
- Keep sample/demo data visibly labelled if it must remain.

Acceptance criteria:

- No UI copy implies regulator certification or comprehensive verification without evidence.
- No analytics value is invented when an API field is absent.
- Empty analytics remain useful through labels, explanations, and next actions without fake numbers.

## Gate 5 - Accessible Forms, Dialogs, and Failures

Goal: make the operational interface understandable to assistive technology and resilient to request failures.

Scope:

- Introduce shared field and dialog conventions where repetition warrants them.
- Give every search, filter, select, and form control a programmatic label.
- Add dialog semantics, labelled titles/descriptions, Escape handling, initial focus, focus return, and background interaction protection.
- Expose fetch and mutation failures visibly, with recovery actions where appropriate.
- Ensure icon-only buttons have accessible names and visible focus states.

Acceptance criteria:

- Primary workflows can be completed with a keyboard.
- Dialog focus is contained and restored correctly.
- Network failures are announced and never fail silently.

## Gate 6 - Make Lead Stage Updates Reversible

Goal: prevent the board from displaying a stage that the server rejected.

Scope:

- Retain the previous lead state before optimistic movement.
- Roll back on non-2xx responses or request exceptions.
- Surface a concise error and provide a retry path.
- Prevent conflicting stage mutations while a lead update is pending.

Acceptance criteria:

- Successful moves persist after refresh.
- Failed moves return to the previous column and announce the failure.
- Focus and drag/pointer interaction remain usable after rollback.

## Gate 7 - Consolidate the Visual System

Goal: replace the current collection of hard-coded effects with a restrained operational design system.

Scope:

- Define semantic color, surface, border, type, spacing, focus, and status tokens for light and dark themes.
- Migrate shared shell, controls, panels, tables, badges, and dialogs to semantic tokens.
- Reserve gold for brand/primary emphasis; use distinct semantic colors for success, warning, danger, and information.
- Reduce decorative gradients, pulse animations, glass effects, hover lifts, excess badges, tiny all-mono copy, and over-rounded containers.
- Respect `prefers-reduced-motion`.

Acceptance criteria:

- Theme switching visibly changes all shared surfaces and controls coherently.
- Text and controls meet WCAG AA contrast targets.
- Information hierarchy relies on spacing, type, and grouping before color or animation.

## Gate 8 - Metadata and UI Regression Coverage

Goal: give routes a clear identity and protect repaired workflow contracts and shell behavior.

Scope:

- Add route-specific document titles/descriptions through App Router metadata boundaries.
- Add focused automated checks for matching, portal URL construction, public-shell isolation, active navigation, optimistic rollback, accessible labels, and honest analytics fallbacks.
- Keep test tooling proportional to this application and compatible with the existing runner.

Acceptance criteria:

- Browser titles identify the current workflow.
- The highest-risk UI behaviors have automated regression checks.
- All existing domain tests continue to pass.

## Gate 9 - Final Verification

Goal: prove the integrated app works after all remediation gates.

Checks:

1. Run the complete existing test suite and all new focused tests.
2. Run a clean production build through completion.
3. Start the app and exercise dashboard, leads, inventory, matching, portals, deals, visits, analytics, attribution, calculator, and one public portal.
4. Capture browser evidence at 320, 375, 414, 768, and 1440 px.
5. Confirm no document-level horizontal overflow, overlapping controls, inaccessible dialogs, false trust claims, failed API contracts, or browser console errors remain.

Completion criteria:

- Tests and production build pass.
- All primary routes complete the responsive browser checks.
- Any dependency on unavailable external services or seed data is documented precisely rather than reported as a pass.
